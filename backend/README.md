# words-memo backend

Account, sync and library server for the wordsLearning app and website: NestJS 12, TypeORM 1 and PostgreSQL.

- **The phone app** stays offline-first. Its SQLite database is the only thing it reads from, and it syncs a copy per account through `/sync`.
- **The website** (`web/`) works directly on that copy through the library routes (`/languages`, `/folders`, `/sets`, `/words`, `/rules`, `/backup`). Its changes reach the phones with their next sync, which live updates (`GET /events`) start right away.
- **Dictionaries**: the Wiktionary `<lang>-ru.db` files live on this server. The app downloads them from `GET /dictionaries/<file>`, and the website looks words up through the API.

## Run

```sh
cp .env.example .env
docker compose up -d db     # PostgreSQL 17 on localhost:5432
npm install
npm run start:dev           # http://localhost:3000, applies migrations on start
```

Everything in Docker: `docker compose up -d --build`. The `api` container mounts the app's `dictionaries/build/` (from `npm run dict:build` in the repo root) as its dictionaries folder.

Without Docker, put the dictionary files in `backend/dictionaries/`, or set `DICTIONARIES_DIR` (e.g. `DICTIONARIES_DIR=../dictionaries/build`).

For the Android emulator or a USB device, run `adb reverse tcp:3000 tcp:3000` so the app's `http://localhost:3000` (see `src/config/sync.ts` in the app) reaches this machine. Release builds need an HTTPS URL there.

| Script | |
|---|---|
| `npm run build` / `npm run start:prod` | compile to `dist/`, run it |
| `npm test` | unit tests (`node --test`, pure modules only) |
| `npm run typecheck` | `tsc --noEmit` |
| `npm run migration:generate -- src/database/migrations/<Name>` | diff the entities against the DB into a new migration, then add its class to `MIGRATIONS` in `src/database/typeorm.options.ts` |
| `npm run migration:run` / `migration:revert` | outside of app start-up |

The package is ESM (Nest 12 is). Relative imports use `.ts` extensions, which `rewriteRelativeImportExtensions` turns into `.js` on build. That way plain Node can run the pure modules and their tests straight from `src/`. Migrations and entities are listed explicitly in `src/database/typeorm.options.ts`, with no globs, and `synchronize` is off.

## Deploy on cPanel

This needs a cPanel host that has **Setup Node.js App** (CloudLinux Node.js Selector / Passenger) and **PostgreSQL Databases**. If PostgreSQL isn't in your cPanel, ask the host to enable it, or use an external PostgreSQL (`DATABASE_URL` can point anywhere).

### 1. Database

1. cPanel → **PostgreSQL Databases**:
   - Create a database, e.g. `words`. cPanel prefixes it to `<cpuser>_words`.
   - Create a user with a strong password, e.g. `<cpuser>_api`.
   - **Add the user to the database** with all privileges.
2. You need PostgreSQL **9.5 or newer** (for `jsonb` and `ON CONFLICT` upserts). IDs are generated by the server, so no extension is needed. cPanel shows the version on the **phpPgAdmin** start page, or ask the host.
3. Your connection string is:
   `postgres://<cpuser>_api:<password>@localhost:5432/<cpuser>_words`
   URL-encode special characters in the password, e.g. `@` → `%40`.

### 2. Build locally

The host only runs the compiled code. Don't install TypeScript or the Nest CLI there.

```sh
cd backend
npm ci
npm run build
```

Upload these files and folders, **without `node_modules`**:

```
app.cjs
dist/
package.json
package-lock.json
```

### 3. Upload

1. cPanel → **File Manager**: create a folder outside `public_html`, e.g. `/home/<cpuser>/words-api`.
2. Upload the files there. The easiest way is to zip them locally, upload the zip, then use **Extract**. FTP/SFTP or `scp` also work.
3. **Dictionaries**: create the folder `dictionaries` inside it (`/home/<cpuser>/words-api/dictionaries`). Upload `de-ru.db` and `en-ru.db` from the repo's `dictionaries/build/` there; `npm run dict:build` in the repo root makes them. They are about 18 and 14 MB. If File Manager's upload limit is lower, zip them first or use FTP. The app downloads them from `https://api.example.com/dictionaries/de-ru.db`; `GET /dictionaries` lists what the server has.

### 4. Create the Node.js app

1. cPanel → **Setup Node.js App** → **Create Application**:

   | Field | Value |
   |---|---|
   | Node.js version | **22.18 or newer**, or 24 if listed (the `engines` field in `package.json`) |
   | Application mode | Production |
   | Application root | `words-api` |
   | Application URL | the domain or subdomain for the API, e.g. `api.example.com` (create the subdomain under **Domains** first) |
   | Application startup file | `app.cjs` |

2. In **Environment variables**, add:

   | Name | Value |
   |---|---|
   | `DATABASE_URL` | the connection string from step 1 |
   | `BODY_LIMIT` | `50mb` |
   | `NODE_ENV` | `production` |

   Don't set `PORT`: Passenger chooses it.
3. Click **Create**, then **Run NPM Install**. It installs the production dependencies into the app's virtual environment, and `node_modules` becomes a symlink there.
4. Click **Restart**. The first start creates the tables (migrations run on start).
5. Open `https://api.example.com/health`. It should return `{"ok":true}`.

If you have SSH or **Terminal**, the app page shows the command to enter its environment, e.g. `source /home/<cpuser>/nodevenv/words-api/22/bin/activate && cd /home/<cpuser>/words-api`. From there `npm install --omit=dev` and `node app.cjs` work too. Note that `node app.cjs` listens on 3000 and is only for checking errors; Passenger runs the real app.

### 5. HTTPS and the app

1. cPanel → **SSL/TLS Status**: run **AutoSSL** for the API domain. Android release builds only allow HTTPS.
2. In the app, set `SYNC_API_URL` in `src/config/sync.ts` to `https://api.example.com`, then build a release.

### Updating

- **Dictionaries**: upload the new `.db` files over the old ones in `dictionaries/`. No restart is needed: the server reopens a file when it changes. If `FORMAT_VERSION` in `scripts/dictionary/schema.ts` changed, release the app with the matching `DICTIONARY_FORMAT` at the same time.

To update the code:

1. Run `npm run build` locally.
2. Upload the new `dist/` (and `package.json` / `package-lock.json` if dependencies changed, then **Run NPM Install**).
3. Click **Restart**, or run `touch tmp/restart.txt` in the app root.

New migrations run on that restart.

### Troubleshooting

- **The app doesn't start**: check the log. In **Setup Node.js App**, the app's `stderr.log` (or `passenger.log`) is in the application root. Common causes:
  - `DATABASE_URL` is wrong.
  - The DB user wasn't added to the database.
  - The Node.js version is older than 22.18.
- **`no pg_hba.conf entry for host "127.0.0.1"`**: the host's PostgreSQL doesn't accept TCP logins from 127.0.0.1, only from its Unix socket. Put the socket directory in `DATABASE_URL` as `host` and leave the host part empty: `postgres://<user>:<password>@/<database>?host=/var/run/postgresql` (on some hosts the directory is `/tmp`; look for the `.s.PGSQL.5432` file). If that fails with `Peer authentication failed`, ask the host to allow password logins for your user, either over the socket or from `127.0.0.1/32`.
- **The app says "The dictionary is not on the server yet (HTTP 404)"**: the file isn't in `dictionaries/` in the application root (or in `DICTIONARIES_DIR`). Names must be exactly `de-ru.db` and `en-ru.db`. `GET /dictionaries` shows what the server finds.
- **Live updates arrive late or all at once**: something in front of Passenger buffers responses (LiteSpeed, nginx, a CDN). Ask the host to turn off response buffering for the API's domain. Clients still get every change with their next sync or refresh.
- **The first sync fails with 413** on a large word list: the web server in front of Passenger has its own request size limit. Ask the host to raise `LimitRequestBody` (Apache) or the LiteSpeed request body limit to at least 50 MB.

## API

All bodies are JSON. Errors look like `{ code?, message }`, and the app branches on `code`.

| | | |
|---|---|---|
| `POST /auth/register` | `{email, password}` | 201 `{token, user}` · 409 `EMAIL_TAKEN` · 400 validation |
| `POST /auth/login` | `{email, password}` | 200 `{token, user}` · 404 `USER_NOT_FOUND` · 401 `WRONG_PASSWORD` |
| `POST /auth/logout` | bearer | 204, revokes the token |
| `GET /auth/me` | bearer | `{id, email}` |
| `POST /sync` | bearer, `SyncRequest` | `SyncResponse` · 409 `SYNC_CURSOR_AHEAD` · 400 `BAD_SYNC_REQUEST` · 401 `UNAUTHORIZED` |
| `POST /shares` | bearer, `{payload}` (the app's backup file, `kind: 'sets'`, ≤ 5 MB) | 201 `{code, expiresAt}` · 400 `BAD_SHARE_PAYLOAD` · 429 `TOO_MANY_SHARES` |
| `GET /shares/:code` | | `{payload, expiresAt}` without using the code · 404 `SHARE_NOT_FOUND` |
| `POST /shares/:code/redeem` | | `{payload, expiresAt}` and the code is gone · 404 `SHARE_NOT_FOUND` |
| `GET /events` | bearer, `X-Client-Id` | server-sent events, see below |
| `GET /health` | | `{ok: true}` |

### Live updates (`GET /events`)

A `text/event-stream` that stays open. On connect it sends `event: changed` with `data: {"version": <the account's sync version>, "tables": []}`; after that, one `changed` event (`tables` = the synced tables written) for every committed write by **another** client: a phone's `/sync` push or a website request. Clients send a random `X-Client-Id` header with every request, and a stream doesn't get the changes made with its own id. `: ping` comments go out every 25 s.

- The phone syncs when `version` is past its cursor; the website refetches the queries of the changed tables.
- Writes publish a Postgres `NOTIFY account_changes` inside their transaction, so it goes out only on commit and reaches every server process; each process `LISTEN`s on one extra connection (`src/events/`).
- The streams are long-lived connections: the host must not buffer responses (the stream sets `X-Accel-Buffering: no` and `Cache-Control: no-transform`).

### Library (the website)

All bearer. Rows are written with the user's next sync version, under the same per-user lock as `/sync`, so phones pull them on their next sync. Deletes are tombstones and cascade the way the app's foreign keys do: a set takes its words, rules and folder links. Errors: 404 `NOT_FOUND`, 409 `PIN_LIMIT` (more than 5 pinned folders or sets per language), 409 `LANGUAGE_NAME_TAKEN`, 400 `BAD_BACKUP`, and 400 for validation with Nest's `message` list.

### Dictionaries (no account needed)

| | | |
|---|---|---|
| `GET /dictionaries` | | `[{language, file, sizeBytes, format, updatedAt}]` |
| `GET /dictionaries/de-ru.db` | | the file, with `Range` (resumable) and `ETag` |
| `GET /dictionaries/:language/search?q=` | | up to 8 entries by prefix of the lemma or any form, umlauts folded |
| `GET /dictionaries/:language/translations?term=` | | Russian translations of the term's main form |

- **Auth**: there's no email confirmation. An email is unique (trimmed, case-insensitive) and the password is at least 6 characters. Passwords are hashed with scrypt (`node:crypto`). Tokens are 32 random bytes; only their SHA-256 is stored (`auth_tokens`). They never expire, and logout deletes them.
- **Sync** (`src/sync/protocol.ts`, mirrored in the app's `src/features/sync/protocol.ts`): one request pushes the phone's changes and pulls everyone else's.
  - Tables: `languages` (custom ones only, keyed by code), `sets`, `folders`, `folderSets` (keyed `folderId:setId`), `words`, `rules`. Each one is `{upserts: Record[], deletes: key[]}`.
  - `cursor: null` is a full sync, used after sign in. The phone sends every row and gets back every live row it didn't send.
  - The phone is the source of truth. Pushed rows overwrite the server's copy without comparing timestamps.
  - Each request that writes gives all its rows the same new `version` (`users.sync_version + 1`). The user row is locked `FOR UPDATE`, so the requests of one user run one at a time. A pull returns rows with `version > cursor`, minus the rows of the current request.
  - Deletions stay as tombstones (`deleted = true`) so other devices can pull them.
  - `SYNC_CURSOR_AHEAD` means the cursor is newer than the server's history (the DB was reset or restored). The app then runs a full sync again.

- **Share codes** (`src/shares/`): a code is 8 characters from `ABCDEFGHJKMNPQRSTUVWXYZ23456789`; lookups ignore case, spaces and dashes. It stores a snapshot of the set, works once (redeem is a single `DELETE … RETURNING`) and for 7 days. One account can hold 100 unused codes. Reading and redeeming need no account, so a future website link works for anyone. Expired rows are deleted on start and every 7 days (the start-up run matters on Passenger, which idles and restarts the app).

## Schema

`users`, `auth_tokens`, `shared_sets` (share codes, see above), plus one table per synced type. Those have the primary key `(user_id, id)`, the app's columns, `version` and `deleted`, with an index on `(user_id, version)`. There are no foreign keys between the content tables: devices push in any order, and the app skips rows whose parent it doesn't have. The library routes (`src/library/`) read the same tables, filtering on `deleted = false`, and write by bumping `version` the same way `/sync` does (`LibraryStore`). `src/library/shared/` and `src/dictionaries/{queries,searchKey,similarWords}.ts` are copies of the app's pure modules (backup format and merge, dictionary queries); keep them in step.
